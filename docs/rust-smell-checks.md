# Deterministic Rust smell checks

The [Refactoring.Guru catalog](https://refactoring.guru/refactoring/smells) links 23 smells, including Incomplete Library Class under Other Smells. We can inventory every one and build deterministic tests for defined Rust rules. We cannot equate a passing collection of size and syntax rules with proof that all 23 semantic smells are absent.

This document is the Rust adaptation and implementation plan, not an installed scanner. The repository has no Cargo workspace, Rust implementation, or pre-commit hook yet. The generic starting policy lives in `examples/quality-policy.json`. Each consuming project owns its checked-in `quality-policy.json`, limits, and exceptions; the additional rules below are proposals, not newly enabled gates.

## What the code-smell hook must report

The requested scanner is a Rust program that recognizes fixed code patterns and reports their measurements against configured thresholds during pre-commit. It must report function and type metrics below the limits as well as violations, so the developer can see how close code is to a limit. Contract tests remain separate behavior checks; a detectable structural pattern does not need a human verdict before it can be reported.

Illustrative output below uses invented symbols and measurements; it is not a scan of this repository:

```text
Smell                Symbol          Metric             Value   Threshold       Result
Long Method          agent_loop      function lines     134     maximum 100     VIOLATION
Long Parameter List  submit          arguments          6       maximum 7       PASS
Large Class          Agent           fields             12      maximum 15      PASS
Large Class          Agent           methods            24      maximum 20      VIOLATION
Large Class          Agent           method code lines  410     maximum 500     PASS
Duplicate Code       parse_a/parse_b  AST similarity     0.91    trigger >=0.82  VIOLATION
Feature Envy         render          foreign access     --      --              NOT_IMPLEMENTED
Refused Bequest      --              class inheritance  --      --              NOT_APPLICABLE
```

Each finding also includes a stable rule ID and source location; duplicate findings identify both functions. JSON carries the same information, including the comparison operator and whether the result blocks the commit. An unavailable metric is `null`, with an explicit reason/status, never a fabricated zero. Findings sort by relative path, line, qualified symbol, and rule ID. Values and limits must name their units; do not combine unrelated smells into one undocumented overall score. CRAP remains its own metric.

The hook invokes this scanner through the quality runner. Existing required gate rules block when their limits are exceeded; other defined pattern detectors may produce reproducible indicators until explicitly adopted as blocking rules. Unsupported or missing **required** detectors fail the check. All 23 catalog entries appear in the coverage inventory even when no generic source-only detector applies.

## Structural detectors beyond size limits

These are proposed fixed pattern definitions to implement and test. Their numbers are proposed detector settings, not additional activated limits in `quality-policy.json`. The first implementations must include matching and nonmatching Rust examples, measured values, and documented scope. Once validated, their settings move into the policy file rather than living as hidden constants in the scanner.

| Smell indicator | Proposed measurable pattern | Proposed trigger |
|---|---|---|
| Primitive Obsession | Raw scalar/string fields or parameters, with aliases resolved; calculate count and share of the relevant declaration's slots. Nominal wrapper types remain distinct. | At least 5 raw scalar/string slots and share ≥80%. |
| Data Clumps | Same group of named, resolved field/parameter types occurs in distinct declarations; count each declaration once. | At least 3 slots repeated in at least 3 declarations. |
| Alternative Classes with Different Interfaces | Structurally similar methods belong to distinct types but expose different names/signatures; report both interfaces and the matching bodies. | At least 1 unexcepted method pair with similarity ≥0.82 and differing interfaces. |
| Temporary Field | Count optional fields accessed by only a small fraction of a type's source-authored methods; resolve direct field accesses and exclude generated methods from the denominator. | At least 3 optional fields, each accessed by ≤25% of at least 4 methods. |
| Switch Statements | Repeated dispatch over the same resolved enum in distinct methods; record arm counts and owners. | At least 3 dispatch sites with at least 4 arms each. |
| Comments | Count ordinary explanatory comment-only lines within a function body, excluding doc comments; retain code-line counts separately. | Comment-line share ≥30% in a function with at least 20 code lines. |
| Data Class | Fields exist but source-authored operations consist only of accessors or there are no operations; derived methods are counted as generated scope. | At least 2 fields and 0 non-accessor operations. |
| Lazy Class | Count fields, source-authored operations, and total method-body code lines; show all three measurements. | At most 1 field, 1 operation, and 5 method-body code lines. |
| Feature Envy | Resolve direct accesses to foreign data versus owned data; calls through effect ports are not classified as foreign field reads. | At least 5 direct foreign-field accesses and foreign-access share >60%. |
| Message Chains | Resolve successive navigation results to declared domain owners; exempt registered iterator, builder, and stream APIs explicitly. | At least 3 owner transitions in one navigation chain. |
| Middle Man | Count methods whose entire body forwards unchanged arguments to a target without additional behavior; show forwarding share and method count. | At least 5 methods and forwarding share ≥80%. |

For these proposed ratios, primitive share is raw scalar/string slots divided by all fields/parameters in the declaration; temporary-field share is the number of distinct methods directly accessing that field divided by the type's source-authored method count; comment share is ordinary comment-only body lines divided by code-plus-ordinary-comment-only body lines; foreign-access share is direct foreign-data accesses divided by direct foreign-plus-owned-data accesses; forwarding share is pure-forwarding methods divided by all source-authored methods. Report numerator and denominator. Do not divide by zero or fabricate a ratio for an empty population. Canonical type identity and the explicit scalar/string type set must be fixed and fixture-tested before these detectors are activated.

These detectors report the matched Rust shape with its value and threshold. Domain roles and exact exceptions can explain legitimate shapes, such as data messages, nominal newtypes, and thin adapters; the matching algorithm remains fixed. Public-API conformance and known library capabilities additionally use configured interface rules. Dead/unused code and forbidden coupling retain their compiler/dependency measurements. Change-history indicators require a pinned history input and defined counting rule; inheritance-only entries have an explicit native-Rust applicability result. None of those entries silently receives a source-pattern score when its input or rule is unavailable.

## Full catalog mapping

"Metric gate" means a fixed project measurement, not a complete semantic diagnosis. "Limited gate" checks a narrower property. "Contract" needs a declared project requirement. "Candidate" can produce reproducible evidence but needs context before making it a blocking policy. "History" requires more than the staged source. Native Rust exclusions must be reported explicitly, never counted as passed tests.

| Smell | Rust rule or evidence to test | Coverage and limitation |
|---|---|---|
| [Long Method](https://refactoring.guru/smells/long-method) | Enforce the pinned Clippy function-line limit of 100; keep CRAP ≤30 using fresh coverage. | Metric gate. Short code can still mix responsibilities. |
| [Large Class](https://refactoring.guru/smells/large-class) | Per struct/enum type: ≤15 fields per struct/variant, ≤20 associated functions, ≤500 total method-body code lines; enums ≤20 variants and traits ≤20 functions. Aggregate all source-authored inherent and trait implementations by qualified type identity. | Metric gate. Requires the missing type checker; method count alone does not establish cohesion. |
| [Primitive Obsession](https://refactoring.guru/smells/primitive-obsession) | Report raw scalar/string slot count and share with the proposed pattern rule. A project-supplied domain-type contract can require nominal wrappers/enums at particular API positions. | Structural indicator plus optional contract. Alias resolution matters; the raw-type pattern does not identify domain meaning. |
| [Long Parameter List](https://refactoring.guru/smells/long-parameter-list) | Enforce pinned Clippy argument-count limit of 7. | Metric gate. Follow the selected tool's receiver/argument convention consistently. |
| [Data Clumps](https://refactoring.guru/smells/data-clumps) | Candidate rule: the same group of at least 3 named, canonically typed fields/parameters appears in at least 3 distinct declarations. Deduplicate declarations before counting. | Candidate. Repetition does not establish shared meaning; changed names can evade a syntax-based rule. The threshold is a proposal. |
| [Alternative Classes with Different Interfaces](https://refactoring.guru/smells/alternative-classes-with-different-interfaces) | Report structurally similar methods on distinct types with differing names/signatures. Registered port roles can additionally require trait conformance and common behavior tests. | Structural indicator plus optional contract. Similar bodies do not prove equivalent behavior. |
| [Refused Bequest](https://refactoring.guru/smells/refused-bequest) | The original subclass-inheritance smell does not directly apply to native Rust. For a trait-related analogue, test each promised capability and reject unexplained placeholder implementations. | Native-Rust exclusion for the original smell; contract checks for an explicitly defined analogue. Macro-emulated inheritance needs separate treatment. |
| [Switch Statements](https://refactoring.guru/smells/switch-statements) | Candidate evidence: repeated dispatch over the same resolved enum/type in distinct owners, overlapping branch bodies, or configured nesting/complexity violations. | Candidate plus existing complexity gates. An ordinary `match` is valid Rust; arm count or a switch token alone does not diagnose this smell. |
| [Temporary Field](https://refactoring.guru/smells/temporary-field) | Report optional fields and their direct method-use share with the proposed pattern rule; declared lifecycle invariants can additionally be tested separately. | Structural indicator plus optional contract. Optional configuration/messages may match a legitimate pattern. |
| [Divergent Change](https://refactoring.guru/smells/divergent-change) | Reproducible history evidence can group changes by owner over a pinned commit range and declared responsibility labels. | History and responsibility contract. A source snapshot or churn count cannot infer unrelated reasons for change. |
| [Parallel Inheritance Hierarchies](https://refactoring.guru/smells/parallel-inheritance-hierarchies) | Native Rust has no ordinary subclass hierarchy. Parallel trait/enum families can be inventoried for synchronized changes over a pinned history range. | Native-Rust exclusion for the original smell. Parallel Rust representations need a separate contextual rule. |
| [Shotgun Surgery](https://refactoring.guru/smells/shotgun-surgery) | History evidence can count owners/files changed together for a declared logical change; compare it with an explicitly configured change contract. | History. A legitimate port/API change can require several adapters to change; touched-file count alone is not a verdict. |
| [Comments](https://refactoring.guru/smells/comments) | Report ordinary comment-only body-line share with the proposed pattern rule; Rustdoc link checks can enforce a separate documentation property. | Structural indicator. The ratio does not judge explanation quality; useful explanations can legitimately match. |
| [Duplicate Code](https://refactoring.guru/smells/duplicate-code) | Block unexcepted function pairs with cargo-crap v0.5.0 normalized-AST similarity ≥0.82, at least 20 normalized nodes. Inspect structured duplicate results separately from the CRAP exit status. | Metric gate. Structural matching drops names/literals and can match unrelated behavior; it is not a semantic-equivalence test. |
| [Data Class](https://refactoring.guru/smells/data-class) | Report types with fields and no non-accessor source-authored operations. Declared roles can additionally identify intentional messages/configuration. | Structural indicator plus optional role contract. A data-only type can fit a project's ports. |
| [Dead Code](https://refactoring.guru/smells/dead-code) | Deny compiler-detected unused private code, unused imports, and unreachable code in the checked target/feature set. Test that suppressions cannot silently bypass required rules. | Limited gate. Exported library APIs, alternative targets/features, macros, and runtime selection limit whole-program conclusions. |
| [Lazy Class](https://refactoring.guru/smells/lazy-class) | Candidate evidence: a tiny type with little behavior or delegation. Compare its declared role with its actual operations. | Candidate. Small newtypes, marker types, and narrow port implementations can be useful. Small size alone is not a failure. |
| [Speculative Generality](https://refactoring.guru/smells/speculative-generality) | Existing unused-code gates and selected Clippy unused-type-parameter checks catch defined cases; inspect unused abstractions against declared use cases. | Limited gate. A one-implementation trait can still be a required port; public extension points need context. |
| [Feature Envy](https://refactoring.guru/smells/feature-envy) | Typed candidate evidence can compare direct foreign-data access with owned-data access, using resolved owners and configured roles. | Candidate requiring type resolution. Calls through configured ports can be expected; raw counts do not establish where behavior belongs. |
| [Inappropriate Intimacy](https://refactoring.guru/smells/inappropriate-intimacy) | Enforce Rust privacy plus the consuming project's workspace dependency map and configured public API boundaries; resolve renamed dependencies and re-exports before classifying accesses. | Limited gate. These catch forbidden access/coupling, not every misuse of intentionally public data. |
| [Incomplete Library Class](https://refactoring.guru/smells/incomplete-library-class) | Compile and run adapter contract tests for the external library capabilities we actually require. | Contract. A scanner cannot invent missing requirements. An extension trait or adapter can legitimately fill a gap. |
| [Message Chains](https://refactoring.guru/smells/message-chains) | A typed candidate rule can count navigation across distinct declared domain owners; configure exclusions for iterator/builder/stream APIs. | Candidate requiring type/role information. Dot count would misclassify idiomatic Rust pipelines. |
| [Middle Man](https://refactoring.guru/smells/middle-man) | Candidate evidence can measure pure forwarding methods and delegated targets; evaluate against declared boundary roles. | Candidate. Adapters and intentional proxies can justify forwarding. Do not require business logic in an adapter to silence this metric. |

The Rust adaptations and proposed measurements above are our inferences, not executable rules or thresholds supplied by Refactoring.Guru. Its [Middle Man](https://refactoring.guru/smells/middle-man), [Comments](https://refactoring.guru/smells/comments), and [Feature Envy](https://refactoring.guru/smells/feature-envy) pages explicitly describe cases where the pattern may be appropriate. The [Rust book](https://doc.rust-lang.org/book/ch18-01-what-is-oo.html) explains structs/enums, implementations, traits, and the lack of ordinary class inheritance.

## Large Class: concrete checker contract

1. Read the staged workspace source and locate source-authored structs, enums, traits, functions, and implementation blocks using a Rust parser/compiler frontend. Evaluate conditional compilation for the recorded native target and production feature set. Analyze the active production declarations; exclude test-only declarations and record inactive/generated scope rather than calling it passed. Regex or brace counting is not adequate for this blocking rule.
2. Identify each local type by its defining crate/module/type. Resolve aliases, imports, and generic implementation targets to that owner; do not merge unrelated types just because they have the same name. Splitting an implementation between files, trait implementations, or generic specializations does not create a new budget for the defining type.
3. Count the policy's fields, variants, and associated functions. Sum method-body code lines across the source-authored functions of that type, excluding blank/comment-only lines using token/source-span information. A line containing both code and a comment counts as code. A source location is counted once within each function. The selected function-line Clippy measurement is separate and must retain its pinned convention.
4. Emit stable rule IDs, qualified symbols, measured values, limits, and relative source locations. For example: `type_functions: core::Agent has 21; limit 20`. Count tests/generated members only according to explicit scope rules; report excluded/generated coverage without pretending those members passed.
5. Compare counts with fixed inclusive maxima. Twenty associated functions pass; twenty-one fail. An exact documented exception can change the verdict. Unknown ownership, parse failure, or an incomplete required measurement is an error, not a pass.

[syn](https://docs.rs/syn/latest/syn/) supplies Rust syntax parsing, not a complete name/type resolver. The implementation must demonstrate alias/owner resolution before enforcing this rule. If compiler information is necessary, [Dylint](https://github.com/trailofbits/dylint) supports custom Rust compiler lint libraries; that is an implementation option to validate with a pinned compatible toolchain, not a ready-made full smell suite. [Cargo metadata](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html) supplies the dependency identities used by the separate architecture rules.

## Checker tests before hook installation

Use tiny Rust fixture workspaces with expected structured findings and exit statuses. These are tests of the checker, separate from tests of a consuming application.

- Field counts 14/15/16; type function counts 19/20/21; type code lines 499/500/501; trait and enum limits at/below/above their maxima.
- One type with 12 functions in each of two files must fail the 20-function limit. The same total split between inherent and trait implementations must also fail.
- Same-named types in different modules remain separate; aliases and generic implementation targets still map to the defining type.
- Comments, blank lines, string/raw-string contents, multiline comments, attributes, and generated-member boundaries follow the token/span convention. Conditional source follows the recorded production target/features: test-only declarations are excluded; mixed test/production conditions are evaluated rather than dropped wholesale. Inactive branches are reported as outside that run's scope. Lock these cases in fixtures before gating.
- Structural duplicate fixtures fail at the configured boundary, with benign shape matches illustrating documented exceptions. A duplicate report can fail even when the CRAP score is below its limit. No duplicate finding is treated as proof of equivalent behavior.
- Renamed forbidden dependencies and unregistered lint suppressions fail. Checked-in exact exceptions behave consistently; malformed, stale, or unknown exceptions fail validation.
- Missing tools, malformed JSON/LCOV, parser failures, unresolved required measurements, and incomplete coverage/scan inputs cannot produce a successful hook result.
- Repeat the same fixture under the same pinned inputs and compare normalized reports and verdicts. Sort paths/findings and keep timestamps outside verdict data.

## Standalone implementation and hook integration order

1. Implement the Rust scanner here as its own executable package using the standard `src/main.rs` entry point. This tool is a development dependency installed separately; it is not a library imported by consuming applications. Its build and detector fixture workspaces must not depend on `tiny` or any other consuming repository.
2. Validate the consuming project's checked-in policy, tool versions, target/features, and required measurements. Implement the function/type measurements, structured duplicate gating, and meaningful detector fixtures. Compiler/type resolution and external analysis tools must be pinned and verified before their results become required gates.
3. Implement the planned `smells check --staged --policy quality-policy.json` interface in `docs/project-integration.md`. Read source and policy from an isolated index snapshot, report deterministic metrics and the 23-item coverage inventory, and propagate violations and errors through nonzero exits. Do not install `hooks/pre-commit.example` until the CLI exists and these behaviors pass fixtures.
4. Implement the additional structural detectors with fixed syntax/type measurements and calibrated fixtures. Put validated detector settings into policy; add project-supplied roles, interfaces, exceptions, or pinned history inputs where needed. No application package names or architecture edges are built into shared rules.
5. Keep a project's overall quality runner responsible for formatting, security scans, test execution, fresh coverage, and other required checks. It invokes this tool for smells and can supply verified coverage/compiler/dependency evidence. If an existing hook already runs that runner, add a call there rather than replacing the hook. Independent OSV, Gitleaks, and application tests are not replaced by this scanner.

Reports distinguish `pass`, `violation`, `error`, `not_implemented`, `needs_contract`, `candidate_only`, and `not_applicable_native_rust`. A required but unimplemented check is an error. A successful measured gate must not label unrelated semantic smells as passed.

Pin source, toolchain/tools, policy/exceptions, feature/target scope, test fixtures/seeds, and coverage/history/compiler inputs to reproduce a verdict. Inherited compiler defaults and source `allow` attributes must not silently disable selected required checks. The existing [compiler lint documentation](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html#dead-code), [Clippy rules](https://rust-lang.github.io/rust-clippy/master/index.html), and [cargo-crap](https://github.com/minikin/cargo-crap) provide pieces, not a verified implementation of the entire Refactoring.Guru catalog.

Smell names do not mandate design patterns. Fixes should preserve tested behavior and use the smallest extraction, move, inline, or type change that addresses the measured problem; introducing Strategy, State, or another pattern requires separate justification.
